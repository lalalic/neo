# Neo CLI migration and service management (local candidate)

Scope: Source implementation in `lalalic/neo`, product identity owned by the existing native NeoY/Neo application. Does **not** create a new scheduler, MCP service, or GUI. Repositories and durable IDs stay separate.

## Current commands

```
neo status
neo doctor
neo project list
neo project resolve NAME
neo skill list [--project PATH]
neo skill package SKILL_DIR OUTPUT.zip
neo queue <legacy queue arguments>
neo escalation --handoff-file PATH [existing options]
neo service list
neo service status NAME
neo service start|stop|restart NAME --apply
```

`project`, `skill`, `queue`, and `escalation` delegate to their existing source owners. Legacy `list-xchat-projects`, `list-xchat-skills`, `neo-queue` and absolute checkout scripts remain compatible during migration; the XChat bootstrap prefers the installed CLI. The `list-xchat-skills` resolver finds its bundled Neo catalog relative to its installed script rather than requiring `~/Workspace/neo`; `NEO_SKILLS_ROOT` is an explicit alternate catalog root for isolated tests/deployment.

## Service manager contract

- `neo service list|status`: read-only PM2 `jlist` plus the existing native NeoY launchd label `com.neox.neoy.keepalive`. Do not expose process environment, secrets, full PM2 configuration, or arbitrary launchd units.
- PM2 entries are returned with process-manager state (`online`/`stopped`/etc.), not asserted capability health. NeoY's launchd state is also process status, not full MCP federation health. Each service has `health:not_checked` until a real owner-specific probe is added.
- `start|stop|restart` only operate on exact, currently discovered service names; they require the literal trailing `--apply`. Invocations use argument vectors without shell interpolation. The CLI never restarts a service merely because it is stopped. A stopped optional watcher is not a failure.
- Native NeoY `restart` uses launchd kickstart and `start` targets the existing registered label; NeoY keepalive `stop` is intentionally refused instead of pretending an individual process kill stops the supervised service. Any full disable/upgrade must follow the native owner's lifecycle procedure.
- `neo status` tests only the local NeoY HTTP gateway landing response and Node/Python executables; `gateway_http:reachable` is **not** an assertion that MCP tools are healthy. `neo doctor` reports actionable missing dependencies. There is no automatic update, secret propagation, or service privilege escalation in this implementation.

## Distribution and collision policy

The **transitional** unscoped global `neo` executable retains its existing name. A local allowlisted candidate is generated by `node scripts/stage-neo-cli.mjs OUTPUT_OUTSIDE_CHECKOUT`; it includes public CLI entrypoints, original escalation contracts, queue implementation and committed shared skill sources (including their scripts and references). Source components stay in `lalalic/neo`; generated package contains no developer runtime data, Git worktrees or private credentials. The skill assets are loaded from committed Git blobs and file modes, excluding unrelated dirty/untracked workspace changes. It requires Node.js 22+ because the legacy queue uses `node:sqlite`, plus Python 3 for XChat skill discovery (PyYAML is optional; a standard-library subset parser covers the required skill contract). The current local candidate version `neo@1.0.2-p0.1` is not an npm-published signed release.

Never silently overwrite a third-party `neo` executable: verify package owner and symlink target first. On the current work node the existing `neo@1.0.1` was backed up under `~/Library/Application Support/NeoY/cli-backups/neo-1.0.1-before-cli-p0-20261022` before installing the local candidate. Reversion requires restoring that package and its prior executable link; do not alter queue SQLite, Relay state, browser profiles or credentials. This is a local reversible transition, not automatic migration on fresh machines.

## Acceptance

- Unit contract: legacy Neo tests plus new CLI/service tests. Synthetic unauthorized inputs are refused.
- Isolated npm tarball installation: run `neo status`, project resolve, skill list and native service status without executing from the developer's Git checkout.
- Legacy compatibility: identical project-resolution JSON; same skill name/requirement selection; queue status in an isolated `NEO_QUEUE_HOME`; synthetic text-only ChatGPT ZIP.
- Live PM2 lifecycle test: create a disposable test service, stop, start, restart, verify manager states, and delete it. No existing production service is restarted for the test.
- Work-node installed CLI: check global `neo` package identity and linked executable; read-only status/doctor and PM2/launchd enumeration.

**Out of scope / NOT_VERIFIED**: app-installer ownership of the public CLI, signed CLI bundle, publication/distribution to other Macs, a complete declarative service desired-state controller, automatic health-gated upgrades, rollback of real services, remote-node E2E, full permission/capability registry and final NeoY→Neo signed app identity migration. These require subsequent work and cannot be claimed complete from this CLI candidate.
